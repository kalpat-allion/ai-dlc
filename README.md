# AI Development Life Cycle (AI-DLC)

> A reusable, phase-by-phase methodology for integrating AI tools into every stage of the software development lifecycle.

This is a documented process that defines **how**, **when**, and **which** AI tools to use across the entire SDLC. It is designed so that any development team can adopt it on any project, with clear human responsibilities, AI integration points, quality gates, and escalation rules at every step.

## Consolidated Tool Stack

A core design principle of this process is **one tool per job**. We deliberately avoid stacking multiple tools that do the same thing. This reduces cost, lowers the learning curve, and eliminates context-switching between overlapping products.

### Foundation Tools (used across multiple phases)

These are paid once per developer and reused across every phase that needs them. They are explicitly listed under each phase below where they apply, so you never have to cross-reference.

| Tool | Subscription | Cost | Used In |
|------|--------------|------|---------|
| **Claude (Max)** | Claude Max (heavy users) / Pro (light users) | $100/mo Max, $20/mo Pro | Phases 1, 2, 3, 4, 5, 6, 7 |
| **Claude Code** | Included in Claude Max; or API usage | Included in Max | Phases 2, 3, 4, 5, 6, 7 |
| **AI PR review** — pick one or both | **CodeRabbit Pro** *and/or* the **Claude PR review bot** (`anthropics/claude-code-action` in your own CI) | $24/mo per seat *and/or* per-run token spend | Phases 3, 4, 5 |
| **Linear** | Linear Standard / Plus | $8–14/user/mo | Phases 1, 3, 4, 7 |
| **GitHub Advanced Security** — Code Security | GHAS Code Security (per active committer) | **Free on public repos; $30/active-committer/mo on private repos** | Phases 3, 5, 6 |
| **Fireflies.ai** | Fireflies Pro | $10/mo | Phase 1 |

**Total per developer: ~$145/mo** (Max + Linear Standard + CodeRabbit) or **~$65/mo** (Pro + Linear Standard + CodeRabbit) — covering ALL AI reasoning, coding, review, and work tracking across all 7 phases. **On a private repo, add $30/active-committer/mo for GHAS Code Security** (~$175/mo and ~$95/mo respectively); on a public repo it is free.

> **GHAS is the one line item this framework will not make free.** CodeQL is the prescribed SAST baseline across Phases 3–5 and Copilot Autofix and Dependabot alerts ride on the same licence, so on a private repo the static-analysis capability is a paid line rather than the free-OSS scanner earlier versions assumed. That is a deliberate trade: one first-party scanner wired into the platform the code already lives on, versus a third-party tool per capability. Budget it per active committer, not per seat — GitHub bills only committers who pushed in the period.

> **AI PR review is mandatory; the reviewer is a per-project choice.** The AI-DLC supports two as peers — neither is a fallback for the other. **CodeRabbit** is a hosted app: flat per-seat cost, near-zero upkeep, vendor-tuned. The **[Claude PR review bot](./aidlc-phases/03-development/PR-REVIEW-BOT.md)** runs `anthropics/claude-code-action` in your own CI and reviews against a checklist committed in the repo, so team conventions are enforced by the same file that documents them (and the same file drives the local pre-PR `code-reviewer` gate) — per-run token cost, and the checklist has to be actively maintained. A project picks whichever fits, or runs both. The selection rule is in [Phase 3 → Step 4.3](./aidlc-phases/03-development/PROCESS.md#step-4-code-review); the totals above assume CodeRabbit, so **subtract $24/mo on a bot-only project** and add its token spend instead.

> **Linear is the project-management spine of the AI-DLC.** Claude Code integrates directly with Linear via the official **Linear MCP server** (`https://mcp.linear.app/mcp`), wired at **project scope** (committed `.mcp.json`) so each repo authenticates independently — you can keep several projects open at once, each under its own Linear account if needed. The PRD itself lives in Linear as a **Linear Document** attached to the Linear Project that owns its work breakdown — Claude Code publishes the PRD, hosts stakeholder review on the Document, scaffolds Milestones, and pushes stories with clickable deep-links back to the PRD's section anchors. PRD, backlog, gap analysis, bug tracking, and release notes all share one continuous, traceable thread inside Linear instead of scattering across Jira / Notion / Confluence / spreadsheets. See [Phase 1 Step 0 setup →](./aidlc-phases/01-requirement-gathering/PROCESS.md#step-0-one-time-setup--connect-claude-to-linear-via-mcp).

### Per-Phase Tool Stack

#### Phase 1 — Requirement Gathering

| Tool | Purpose | Subscription / Cost |
|------|---------|---------------------|
| **Claude (Max)** | PRD drafting, user stories, acceptance criteria, gap analysis, scalability/cost assessment — run in **Claude Code** (funded by the Max/Pro subscription) with the **Linear MCP server connected** for context pull and backlog scaffolding | Foundation (~$100/mo Max or $20/mo Pro) |

#### Phase 2 — System Design

| Tool | Purpose | Subscription / Cost |
|------|---------|---------------------|
| **Claude (Max)** | Architecture proposals, ADRs, trade-off analysis, design review, tech stack decisions, API contract drafting | Foundation |
| **Claude Code** | Schema generation, OpenAPI spec generation, Mermaid C4 / sequence / ER diagrams from existing codebases | Foundation (in Max) |
| **frontend-design Skill** (in Claude Code) | Primary UI/UX wireframing — generates screens as **real code in the repo** (React / Tailwind / shadcn), inheriting the project design system from the codebase; promote mature components straight into the shared library. Paired with **Figma via the official Figma MCP** for designer-led / pixel-perfect canvas work (design-to-code + code-to-design). | Included in Claude Code; Figma on the project's Figma plan |
| **Eraser.io** | Architecture / sequence / ER / cloud / BPMN diagrams — driven from inside Claude via the **official Eraser MCP** (`https://app.eraser.io/api/mcp`), no separate-tool context-switch. Business tier recommended for client work (SOC 2 Type II + audit log). | Free 5 AI generations; Business $15/user/mo |

> **Phase 2 UI/UX tooling.** UI is generated **as repo code** by the **frontend-design Skill in Claude Code**, inheriting the project's design system; **Figma (via the official Figma MCP)** is the paired canvas for designer-led or pixel-perfect work, keeping code and design in sync in both directions. v0 / Bolt / Lovable remain narrower escalation fallbacks, each recorded in the ADR for that flow. See [Phase 2 PROCESS.md → Step 4](./aidlc-phases/02-system-design/PROCESS.md#step-4-uiux-wireframing--in-claude-code).

#### Phase 3 — Development

| Tool | Purpose | Subscription / Cost |
|------|---------|---------------------|
| **Claude Code** | Primary AI coding agent (terminal + IDE extension): scaffolding, multi-file editing, complex refactoring, debugging, doc generation, MCP integrations (Linear, Figma, GitHub) | Foundation (in Max) |
| **Claude Code specialist subagents** (`linear-task-agent`, `frontend-engineer`, `backend-engineer`, `code-reviewer`, `refactor-specialist`) | Scoped, role-aware Claude Code sessions committed under `.claude/agents/` — `linear-task-agent` orchestrates the daily Linear → branch → PR loop; the four implementer/reviewer specialists carry the Phase 3 prompts with repo-specific calibration. Templates in [`aidlc-phases/03-development/subagent-prompts/`](./aidlc-phases/03-development/subagent-prompts/) | Foundation (in Max) |
| **Claude (Max)** | Effort estimation, design clarification, architecture-aware reasoning during coding | Foundation |
| **AI PR review — configure one or both** ([selection rule →](./aidlc-phases/03-development/PROCESS.md#step-4-code-review)) | **CodeRabbit** — hosted app; general bugs, security smells, code quality, and test gaps reasoned from the diff; near-zero upkeep.<br>**Claude PR review bot** — `anthropics/claude-code-action` in your own CI; reviews against a checklist committed in the repo (`.claude/prompts/pr-review-checklist.md`) that also drives the local pre-PR `code-reviewer` gate, catching team conventions, domain invariants, and architectural drift; needs checklist upkeep. Full spec in [`PR-REVIEW-BOT.md`](./aidlc-phases/03-development/PR-REVIEW-BOT.md).<br>Both are advisory (never approve) and never required status checks. | CodeRabbit $24/mo per seat; bot is Foundation (in Max) + per-run token spend |
| **CodeQL (GitHub Advanced Security)** | Static analysis (SAST) in CI — the single SAST scanner across Phases 3–5, governed in Phase 5. Deterministic whole-repo scan on PR and on schedule, SARIF results in the Security tab, custom queries in QL | Free on public repos; $30/active-committer/mo (GHAS Code Security) on private repos |

> **Optional inline completion.** Claude Code is a request-response agent, not a ghost-text autocompleter. Teams that want inline as-you-type completion can add **Supermaven standalone** (free tier or ~$10/mo Pro) or their IDE's native completion alongside Claude Code — optional, and it changes none of the decision rules, gates, or quality bars.

### Why Not More Tools?

| Eliminated Tool | Reason | What Covers It Instead |
|----------------|--------|----------------------|
| GitHub Copilot (as the primary coding assistant) | Overlaps with Claude Code's agentic + inline coding capabilities | **Claude Code** (coding agent); Copilot Autofix / pipeline generation still used in Phases 5–6 |
| ChatPRD | Overlaps with Claude + our standardised prompt templates | **Claude** + prompt templates in this repo |
| Notion / Confluence (for the PRD) | Linear Documents now hold the PRD natively, attached to the same Project that owns the Milestones and Issues — no separate doc tool needed for the PRD-to-backlog flow | **Linear Documents** (Project-scoped, stable section anchors, comment-able by Guests). Notion/Confluence remain optional for company-wide knowledge bases unrelated to a specific PRD. |
| v0 / Bolt.new (as primary UI design tool) | Overlaps with the frontend-design Skill, which generates UI as repo code inheriting the project's design system | **frontend-design Skill in Claude Code** for wireframes and production components, **Figma (via MCP)** for canvas work; v0 / Bolt stay as narrow fallbacks; **Claude Code** is the primary tool for general dev (Phase 3) |
| Stoplight | Overlaps with Claude Code for OpenAPI spec generation | **Claude Code** generates specs → view in free **Swagger UI** |
| Perplexity AI | Overlaps with Claude's knowledge; web search covers the rest | **Claude** + manual web research when needed |
| Swimm | Overlaps with Claude Code for documentation generation; no MCP server, so Claude can't query the published site | **Claude Code** generates docs → publish with **Mintlify** (primary, hosted MCP) or **Docusaurus** (free, repo-resident dev docs) |
| Pulumi (engine, Neo, Copilot, MCP server, Cloud, ESC, Deployments, Insights, `pulumi/*` Actions) | The prescribed IaC stack consolidated on one HCL toolchain: the largest provider ecosystem, native `terraform test`, cost-on-PR through Infracost with no vendor bridge, and a **$0 control plane** running in the project's own cloud account. The licensing question Pulumi's Apache 2.0 answered is now an explicit Step 1 ADR (BSL 1.1 vs MPL 2.0) rather than a tool choice | **Terraform / OpenTofu** + the `terraform-iac-engineer` subagent and the IaC bring-up skills; **Infracost** for cost; **cloud-native remote state + IAM + cloud audit + GitHub audit** for state, RBAC and the trail; **GitHub OIDC + the project's secret manager** for secrets. **Cross-stack resource search, dynamic short-lived non-cloud credentials, and language-native infra unit testing have no inheritor** — see the [Phase 6 risk register](./aidlc-phases/06-cicd-devops/PROCESS.md#risks--guardrails) |

| Primary | Alternative | Notes |

| Claude Code | Aider (free, BYOK) or Cline (free VS Code extension, BYOK) | Open-source agents; bring your own API key |

| Fireflies.ai | Fathom (free unlimited) or Otter.ai ($17/mo) | Fathom is best budget option |
| Terraform (BSL 1.1) | OpenTofu (MPL 2.0) | Drop-in CLI: same HCL, same state format, same provider protocol. The fallback for clients or policies that require OSI-approved licensing end to end — decided as a Step 1 ADR, per [Phase 6 Step 1.2](./aidlc-phases/06-cicd-devops/PROCESS.md#step-1-infrastructure-tech-stack-selection) |
| Cloud-native remote state + GitHub Actions OIDC | HCP Terraform or Spacelift | A managed control plane buys away ops burden, not compliance. The prescribed cloud-native path costs $0 and passes every Phase 6 gate |

## How to Use This Repository

### For a new project:
1. **Set up the tool stack** — Ensure every team member has: Claude (Max or Pro) with **Claude Code** installed, an AI PR reviewer configured on each repo (CodeRabbit and/or the [Claude PR review bot](./aidlc-phases/03-development/PR-REVIEW-BOT.md) — [pick per project](./aidlc-phases/03-development/PROCESS.md#step-4-code-review)), **Linear workspace access**, an **Eraser.io** workspace (Business tier for client work), Fireflies.ai for meetings, and **GitHub Advanced Security enabled on the repo** so CodeQL runs in CI (with Copilot Autofix and Dependabot alerts on the same licence). *(Phase 2 UI/UX is generated as repo code by the **frontend-design Skill** in Claude Code; connect the **Figma MCP** if the project uses Figma as its design canvas. See [Phase 2 Step 4](./aidlc-phases/02-system-design/PROCESS.md#step-4-uiux-wireframing--in-claude-code).)*
2. **Connect Claude Code to Linear via project-scoped MCP** — follow [Phase 1 Step 0](./aidlc-phases/01-requirement-gathering/PROCESS.md#step-0-one-time-setup--connect-claude-to-linear-via-mcp): `claude mcp add --scope project` writes a committed `.mcp.json`, then each developer authenticates once per project via `/mcp`. Because config and auth are per-project, developers can work on multiple projects concurrently, each under its own account. This integration powers backlog automation across phases 1, 3, 4, and 7.
3. **Connect Claude Code to Eraser via project-scoped MCP** — follow [Phase 2 Step 0](./aidlc-phases/02-system-design/PROCESS.md#step-0-one-time-setup--connect-claude-to-eraser-via-mcp) once per repo and once per architect per project. This drives all system-design diagramming from inside Claude Code.
4. **Install the phase subagents and skills** — copy the templates from each phase's `subagent-prompts/` and `skill-prompts/` directories into the consuming repo's `.claude/agents/` and `.claude/skills/` directories, fill the placeholders (`{{TEAM_STACK}}`, `{{COMPONENT_LIBRARY_PATH}}`, `{{TEST_RUNNER}}`, `{{TF_CLI}}`, `{{CLOUD_PROVIDER}}`, etc.), and commit — they are project artefacts, not personal config, and they transfer with the repo at Phase 7. Phase 1 ships the three requirement skills that perform its Linear writes ([`01-requirement-gathering/skill-prompts/`](./aidlc-phases/01-requirement-gathering/skill-prompts/)); Phase 3 ships the development specialists ([`03-development/subagent-prompts/`](./aidlc-phases/03-development/subagent-prompts/)); Phase 6 ships the DevOps set ([`06-cicd-devops/subagent-prompts/`](./aidlc-phases/06-cicd-devops/subagent-prompts/) and [`06-cicd-devops/skill-prompts/`](./aidlc-phases/06-cicd-devops/skill-prompts/)). Note that **skills are folders, not files** — copy the directory so the folder name matches the `name:` field, or the skill silently never loads. Verify subagents with `/agents`; verify skills by confirming each appears in the available-skills list. See each directory's README for the full instantiation checklist, [`docs/PLACEHOLDERS.md`](./docs/PLACEHOLDERS.md) for the placeholders that appear under different names in different phases and must be filled with the same value, and [`docs/ROUTING.md`](./docs/ROUTING.md) for which artifact owns which work once several are installed together. **Fill `{{CLOUD_PROVIDER}}` and `{{TF_CLI}}` before running any Phase 6 IaC helper** — a guessed infrastructure setting is the one mistake in the framework with no cheap undo.
5. **Read the PROCESS.md** for each phase sequentially as you progress through the SDLC.
6. **Copy prompt templates** from PROMPTS.md into your project's prompt library. Customise placeholders for your project.
7. **Configure quality gates** from QUALITY-GATES.md in your CI/CD pipeline and review process.

### For adopting on an existing project:
1. Identify which phase you are currently in.
2. Read that phase's PROCESS.md and adopt the workflows that apply.
3. Gradually introduce prompt templates and quality gates.

## Key Principles

1. **One tool per job.** Don't stack overlapping tools. Reduce cost and complexity by using each tool for what it does best.
2. **AI assists, humans decide.** Every AI-generated artifact passes through human review before it is considered complete.
3. **Prompts are standardised, not improvised.** The prompt library ensures consistent output regardless of which team member runs the prompt.
4. **Quality gates are non-negotiable.** No phase output advances without passing its defined checklist.
5. **Claude Code is the backbone.** One AI surface handles reasoning across all phases — requirements, design, development, review — with MCP servers wired per project so concurrent projects stay isolated. This means one learning curve, one subscription, one surface, one set of conventions.

Its one non-redundant part, judging whether a cost-bearing change is *justified*, survives as the reviewer checklist in `cost-guardrails-bringup` and the self-check in `terraform-iac-engineer`. **Three capabilities have no inheritor and are stated plainly rather than papered over.** *Cross-stack / org-wide resource search and compliance query* (Pulumi Insights and the MCP `resource-search` tool) is gone — the documented path is cloud-native inventory (AWS Resource Explorer / Config, Azure Resource Graph, GCP Cloud Asset Inventory), which is **not assessed in `docs/tools-evaluation/`** and is therefore flagged as an evaluation gap, and the mandatory tag set in `AGENTS.md` is promoted from convention to load-bearing control because an untagged resource is invisible to it. *Dynamic, short-lived credentials and immutable secret revisions* (Pulumi ESC) are gone: GitHub OIDC covers every **cloud** credential and is strictly better than ESC there, but third-party API keys (Anthropic, Datadog, Grafana) now sit as **static, long-lived secrets** in the project's secret manager or a GitHub Environment-scoped secret, with rotation a scheduled task owned by a named human rather than a property of the system. *Language-native infrastructure unit testing* is gone: `terraform validate` plus native `terraform test` (`.tftest.hcl` with `mock_provider`, plan-mode run blocks only) is the prescribed replacement — first-party, free, no new vendor — and is materially less expressive than pytest or Jest over component resources; Terratest is deliberately not prescribed. The old Step 3.3 claim that "this is where Pulumi pulls ahead of Terraform — no Terratest gymnastics" was **deleted, not softened**. **The Terraform-BSL-1.1-vs-OpenTofu-MPL-2.0 question is relocated, not deleted** — it moves from "the reason we chose Pulumi" into an explicit **Step 1.2 ADR** that also records, in full, the three reasons Pulumi was originally prescribed, so a reader can see the trade rather than infer it. **State backend joins cloud provider, IaC licence, orchestration, observability, secrets and deployment strategy as an ADR pillar in its own right.** Phase 6 Step 0 drops from seven sub-steps to six: `0.1` (Pulumi MCP) is deleted with **nothing** in its place — the phase's MCP roster is now GitHub plus observability only, and no IaC MCP server is prescribed, `hashicorp/terraform-mcp-server` being registry-docs oriented and unassessed — `0.4` (Pulumi ESC) is absorbed into Step 3, and a new final `0.6` installs the Phase 6 helpers. Step 3 is retitled **"Infrastructure Provisioning (IaC) with Terraform"** (its GFM anchor and the FLOWCHART reference to it change together). **Phase 6 becomes the second phase to ship subagent templates and the first to ship skill templates** — eight new artifacts under `aidlc-phases/06-cicd-devops/subagent-prompts/` and `skill-prompts/`, each wired into PROCESS, FLOWCHART and QUALITY-GATES with a committed-and-smoke-tested checkbox on its gate: `terraform-iac-engineer` (Step 3.2 · Gate 1), `container-image-engineer` (Step 5.1 · Gate 3), `iac-state-backend-bringup` and `ci-identity-and-secrets-bringup` (Step 3 · Gate 1), `cost-guardrails-bringup` (Step 2 · Gate 1), `cicd-pipeline-bringup` (Step 4 · Gate 2), `observability-bringup` (Step 6 · Gate 4), `deploy-and-rollback-bringup` (Step 7 · Gate 5). Two honesty properties are built into the templates rather than left to review: `container-image-engineer` **self-certifies seven of Gate 3's nine criteria and names the other two by owner**, because the image-size comparison is the exact claim its no-scanner boundary forbids and the Gordon review is a different tool; and `terraform-iac-engineer` is forbidden from writing a `terraform test` run block with `command = apply`, which provisions real infrastructure and is the most plausible way an agent breaks the never-apply rule while believing it is testing. **New Phase 6 risk rows** cover state-file blast radius (state holds resource IDs and provider secrets in plaintext and nothing in the stack scans it), `terraform apply` from a laptop, static long-lived third-party secrets, the absent cross-stack search, provider version drift, casual `terraform force-unlock`, the fact that **rollback is re-applying an earlier commit and therefore only works when that commit is still applyable**, and the high blast radius of the bring-up skills that author the backend and IAM trust policy. **The "Pulumi Neo PR acceptance rate" metric becomes "`terraform-iac-engineer` PR acceptance rate"**, joined by a new **plan-to-apply divergence** metric (target 0 — every apply matches the plan a human reviewed). **Phase 7's infrastructure handoff is rewritten** from Pulumi Cloud workspace transfer to state-backend transfer — `terraform init -migrate-state` into the recipient's own backend as the default, verified by `terraform plan` reporting no changes, with a mandatory pre-migration `terraform state pull` backup treated as a credential, a ~15-minute freeze window, the drift workflow disabled during migration, and the CI OIDC trust policy re-pointed to the recipient's identity; the reproducibility demo's corrupted-state drill becomes a **bucket-version restore plus a safe `force-unlock`**, rehearsed rather than documented because there is no vendor-side version history to fall back on. **Phase 7's `FLOWCHART.md` Gate S no longer requires a `pulumi` MCP server to be connected before Phase 7 can start** — left unedited it would have deadlocked the phase on a server that no longer exists. **Phase 7's `QUALITY-GATES.md` needed no edit and is now consistent for the first time**: it has always said "Terraform state backend migration plan documented" and "Terraform state migrated successfully" while its own PROCESS.md prescribed Pulumi Cloud, and the Terraform move resolves that contradiction rather than creating one. Phase 5 loses its two Pulumi Insights cross-links (replaced by Infracost) and drops Pulumi from the two already-vendor-neutral IaC file-type lists. Two pre-existing defects are fixed in passing: the Phase 6 QUALITY-GATES intro said "five gates" while six were defined and mis-mapped Step 3 to its own gate, and `software-architect.md` routed to a `pr-reviewer` subagent slug that exists nowhere in the repo. `/docs/runbooks/` is split into `alerts/` (Phase 6-owned, filename derived from the backend's alert name kebab-cased, which turns Gate 4's runbook check from an eyeball into a script) and `services/` (Phase 3-owned), with Phase 7 a consumer of both and owner of neither.
