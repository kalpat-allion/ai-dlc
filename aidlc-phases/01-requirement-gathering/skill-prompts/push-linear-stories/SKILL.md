# Push user stories into Linear

You are turning approved epics into a reviewable backlog. The source of truth is the **approved PRD Linear Document**; every issue you create must cite the section of it that justifies the story, as a link a reviewer can click. A story with no citation is unverifiable scope, and this skill will not create one.

## Procedure

1. Confirm all four inputs: the Linear Project URL, the PRD Document URL, the **section-anchor map**, and the **epic-to-Milestone mapping**. **Refuse if the anchor map or the Milestone mapping is missing** — without them every deep-link and every parent is a guess. Both come from the two skills that run before this one.
2. For each epic, draft its stories from the PRD sections that epic covers. Rules: each story independently deliverable in roughly 1–3 days; **what, not how** — no implementation detail; error handling and edge cases get stories of their own rather than being buried as footnotes; nothing larger than XL, decompose anything bigger; full coverage of the epic with no gaps.
3. For each story write acceptance criteria in **Given / When / Then** form covering: happy path (2–3 scenarios) · validation and errors (invalid input, missing fields) · boundary conditions (min/max, empty states, character limits) · edge cases (concurrency, timeouts, partial data) · permissions (unauthorised access, role restrictions) · a performance expectation · accessibility (keyboard, screen reader) where the story is UI-facing. **Minimum three criteria — happy path, error, edge case.** A QA engineer must be able to write the test from the line without asking a follow-up question.
4. **Duplicate pre-flight — read-only.** Read the existing issues on the Project *and* on its parent Initiative. Compare every drafted story against them on title and on overlapping acceptance criteria. List each likely duplicate with the existing issue ID and **do not create it**; the PM resolves. Re-running this skill after a partial push is normal and expected — this step is what makes the re-run safe.
5. **Confirm before writing** (see below), then wait for a literal `go`.
6. On `go`, create one Linear issue per story:
   - **State:** `Triage`. Never `In Progress` or beyond.
   - **Milestone / parent:** per the mapping.
   - **Labels:** `phase:requirements`, `ai-generated`, `needs-human-review`, plus `nfr` for a non-functional requirement and `gap-analysis` for a story the PM accepted out of a gap finding.
   - **Description:**
     ```
     **As a** [persona], **I want** [goal], **So that** [benefit].

     ## Acceptance Criteria
     - **Given** … **When** … **Then** …

     ---
     **PRD section:** [§X.Y](<DOCUMENT-URL>#<anchor>)
     **Priority:** Must / Should / Nice
     **Size:** S / M / L / XL
     **Source:** Generated by Claude via the Linear MCP server
     ```
7. **Verify each deep-link you wrote actually resolves** to the heading it names, using the anchor map read back from the Document. Return an audit table: Issue ID · Title · URL · PRD §X.Y deep-link — so the PM can audit by clicking.
8. Stop. → **Gate 3.** The PM works the AI Inbox view (`ai-generated AND needs-human-review`), clicks each deep-link, corrects the story, then removes the label and moves it to `Backlog` to accept. You do not do any part of that.

## Confirm-before-write

Echo the full push as one table and require a literal `go`:

| # | Title | Milestone | Labels | PRD §X.Y → anchor URL | Duplicate? |

Rows flagged as duplicates stay in the table and are **excluded from the write** — show what you are skipping, not just what you are creating.

## Refusal cases

- Anchor map or Milestone mapping missing → refuse.
- **A story with no valid `§X.Y` entry in the anchor map is not created.** Report which story and why; never fabricate an anchor, and never fall back to linking the Document root.
- **Never set state beyond `Triage` / `Backlog`**, and never move an issue between states.
- **Never edit, re-label, re-parent or close an existing issue** — including one you created on an earlier run. Corrections go through the PM in the AI Inbox.
- Never create Milestones, and never touch the Project or the Document.
- Never push scope the PRD does not contain. If drafting surfaced a genuine gap, report it; adding it here bypasses PRD approval.
- **Never remove `needs-human-review` and never move a story to `Backlog` yourself** — that label is the human gate, and clearing it is the acceptance it is meant to record.
- Asked to create issues directly from a gap sweep's findings → refuse until the PM has accepted specific findings and the PRD Document has been updated to contain them.
