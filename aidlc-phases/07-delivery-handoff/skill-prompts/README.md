# Phase 7 Delivery & Handoff Skill Prompts

This directory holds the **`SKILL.md` template** for the Phase 7 documentation skill referenced in [`../PROCESS.md`](../PROCESS.md) (Step 2, Documentation Finalisation). It is a template, not an active skill — Claude Code only auto-discovers folders under `.claude/skills/`.

The skill encodes **one ordered procedure**. Unlike the [Phase 7 handoff subagent](../subagent-prompts/), which is invoked by name, **a skill auto-triggers from its description alone.** That makes the `description:` field the entire routing surface — read [Routing](#routing) before editing it, because this description was narrowed at build time in three places for exactly that reason.

**It does not earn its keep by saving typing.** It exists because page generation and the completeness audit are one loop and are almost always run as two jobs — generate a batch of pages, declare the docs done, and run the audit later or never. The audit's findings *are* the next generation pass's input, and the loop is what the documentation gate measures.

## Files

| Folder | Procedure | Gate | Wraps |
|--------|-----------|------|-------|
| [`finalise-documentation/`](./finalise-documentation/SKILL.md) | Read the build configuration and the existing page tree, agree the section structure, generate each page from cited sources, render the API reference from the specification, run the completeness audit, loop every Critical and High gap back into generation, run the link check, stop for human accuracy review before publish | [Gate 2 (Documentation Complete)](../QUALITY-GATES.md#gate-2-documentation-complete) — **fifteen of its nineteen items**; the other four are named by owner in the template | [`documentation-generation-per-page`](../PROMPTS.md#documentation-generation-per-page), [`doc-completeness-check`](../PROMPTS.md#doc-completeness-check) |

The **Wraps** column is this directory's purpose. Because shipped templates must stand alone in a consuming repo that has no `aidlc-phases/` tree, the skill **inlines** its procedure with `{{PLACEHOLDERS}}` rather than linking back to `PROMPTS.md` — so this table is the only record of where the procedure came from. Keep it current, or the round-trip is lost.

> **Fifteen of nineteen, and the four are named.** Gate 2 carries thirteen required sections and six quality checks. The skill can honestly report fifteen; it cannot certify **runbook-per-alert** (that needs the live alert list, and an alert configured in the backend but never committed as code is invisible to any repository read), **human review of auto-generated content** (it wrote the content, which makes it the wrong reader), **screenshot and diagram currency** (it cannot see a rendered screen), or **the site being deployed and searchable** (it stops before publish by design). The template enforces this with a table rather than a bullet, on the seven-of-nine precedent from `container-image-engineer` — a template built to claim all nineteen would have manufactured a gate pass, which is the failure this whole directory set exists to prevent.

> **Two prompts in this phase deliberately have no skill here.** [`knowledge-base-seeding-faq-glossary-troubleshooting`](../PROMPTS.md#knowledge-base-seeding-faq--glossary--troubleshooting) and the [`quarterly-kb-completeness-check`](../PROMPTS.md#quarterly-kb-completeness-check) both act on a **live knowledge base**, not on the repository — a different surface, a different owner, and in the quarterly case a run that happens 90+ days after the delivery team has left. The documentation skill excludes both by phrase; do not widen it to cover them.

## How to instantiate per repo

1. Copy the **folder** into `.claude/skills/finalise-documentation/` at the consuming repo root, preserving the folder name. **The folder name must equal the `name:` field** — Claude Code uses the folder name as the invocation slug, and a mismatch means the skill silently never loads. Use `cp -r`; globbing the Markdown files flattens the structure and produces zero working skills.
2. Replace the placeholders with the repo's values:
   - `{{DOCS_DIR}}` — the **documentation site's page root**, e.g. `docs/`, `apps/docs/content/`, `website/docs/`. This is the skill's entire write scope. **It is not a general "docs folder"**: `{{ADR_DIR}}`, `{{ARCHITECTURE_DIR}}` and any requirement directory are read-only sources that may or may not sit inside it, and the skill links to them rather than rewriting them
   - `{{API_SPEC_PATH}}` — the API specification the reference pages render from, e.g. `docs/api/openapi.yaml`. **Same value the Phase 3 and Phase 4 templates use.** The skill refuses to hand-write anything that renders from this file
   - `{{ADR_DIR}}` — where decision records live, e.g. `docs/adrs/`. Linked from the architecture section, never copied into it. **Same value `/adr` writes into**
3. **The docs platform is not a fill, and neither is the link checker.** The skill's step 1 **reads the docs build configuration** to learn which platform this repo uses and what navigation and voice already exist, and its step 8 runs whatever link check the repository configures — reporting the item **unverified** when none is. Both were drafted as placeholders and withdrawn: the platform because a value filled at install goes stale the day the repo migrates and nothing notices, while a config read cannot; the link checker because a fill scoped to internal links only would let *"links work (no 404s)"* pass over a set of dead external ones, with no surface anywhere showing it. That is a **pass made reachable that should not be** — the `{{PERF_TEST_ENV}}` failure direction, arriving through a narrow fill rather than a wrong one.
4. **The alert-runbook directory is deliberately not a placeholder either.** The Phase 6 observability skill writes that path as a literal, and coining a name for it here would create the *one fact, one literal and one name* case [PLACEHOLDERS.md](../../../docs/PLACEHOLDERS.md#one-hardcoded-counterpart--worse-than-a-synonym-pair) calls its blindest spot — invisible to every check that starts by grepping for `{{...}}`. The skill locates runbooks by reading, links to them, and **refuses to author or rewrite one**.
5. **The skill needs no MCP server and makes no tracker write.** It runs against the repository and the docs build. Medium and Low gaps are *reported with an owner* for a human to file; do not wire the skill to file them itself.
6. Commit `.claude/skills/finalise-documentation/SKILL.md` to the repo — skills at project scope are shared team infrastructure; treat edits as code changes requiring review.
7. **Verify. `/agents` does not list skills** — skills are a different surface and are verified differently. Run all four checks:
   - **Discovery.** Open a Claude Code session; the skill appears in the available-skills list under its slug. If not, the folder name and the `name:` field are out of alignment.
   - **Explicit invocation.** Type `/finalise-documentation` with a representative input. The procedure should run top-to-bottom and stop at the human accuracy review, **before** anything publishes.
   - **Auto-trigger, in messy language.** This is the check that matters, because the description is the whole routing surface: *"we're handing this over in two weeks and the docs are a mess, where do we even start"* and *"someone asked how to run this locally and we've got nothing written down"*.
   - **Refusal.** Drive the skill into its sharpest refusals and confirm it redirects rather than complies: *"just publish it, we'll review after"*, *"the OpenAPI file is a pain, write the endpoint docs by hand"*, *"write us a DR plan, make something sensible up"*, and *"tick the review box, I'll read it later"*. The last two are the important ones — a fabricated disaster-recovery plan and a self-ticked review box both read exactly like the real thing.
8. **Negative-routing check, once, after installing.** Ask for ordinary work this skill must not claim — *"document this module"*, *"write the README for src/orders"*, *"add a comment explaining this function"*, *"write the runbook for the high-latency alert"*, *"our Confluence FAQ is out of date"*, *"generate the handoff document"* — and confirm it does not load on any of them. **The first two and the last are the ones to watch**; see [Routing](#routing).

## Routing

Skills auto-trigger; subagents do not. A skill whose trigger phrases reuse a verb an existing artifact already claims **wins that route by default and hijacks ordinary work.** Three narrowings were made at build time and all three are worth reading before editing the description.

- **It must never carry a bare *"document this"*, *"write the docs for X"* against a code path, or *"write the README"*.** The repo's module-documentation command owns one module's `README.md` and its inline comments inside a feature story. That command carries `disable-model-invocation: true` today, **so it would not compete for the utterance — it would simply lose it silently**, and the developer would get a whole-site documentation procedure in the middle of a story. The exclusion is written **by work type, not by slug**: a cross-phase slug dangles in a repo that installed Phase 7 without Phase 3, and a dangling pointer in a shipped template is a defect this repo has already paid for twice.
- **It must never carry *"write the runbook"*.** That verb belongs to the Phase 6 observability bring-up when the runbook is alert-triggered. This skill links alert runbooks and is forbidden from authoring or rewriting one — a documentation pass rewriting a runbook produces a runbook that no longer matches the alert that fires it.
- **It must never carry a bare *"we need docs for the handoff"* without the documentation qualifier.** The sibling handoff subagent owns the handoff document and the retrospective, and *"docs"* and *"handoff"* in one sentence speak both artifacts' language. The seam is **write type and audience**: this skill writes **pages on a published documentation site**; the subagent writes **one synthesised deliverable for a receiving team** that is never published to that site. Both descriptions state the seam that way, and **neither names the other by slug** — this phase ships across two directories and installation is per-directory.

| Skill | Owns | Explicitly does not own |
|---|---|---|
| `finalise-documentation` | The published documentation set: the section structure, every generated page, the spec-rendered API reference, the completeness audit and its gap list, the link check, and the stop before publish | One module's README or its inline comments, hand-written API reference content, the API specification itself, any alert runbook, the live knowledge base, the handoff document and the retrospective, and the publish itself |

**One lane in this phase was reserved from the other side, and that is a decision rather than luck.** The Phase 6 observability skill already owns alert runbooks by file path, so no coordinated edit was needed to keep this skill off them. **A deliberately reserved lane reads identically to an oversight unless it is written down** — do not "tidy" either exclusion out.

**This skill is not scoped to a stage of the project.** Documentation is finished before a delivery, and it is gap-checked again whenever somebody asks what is missing — in month one or month nine. The cross-phase version of the ownership table lives in [`docs/ROUTING.md`](../../../docs/ROUTING.md); placeholder names that recur under other spellings elsewhere are reconciled in [`docs/PLACEHOLDERS.md`](../../../docs/PLACEHOLDERS.md).

**A collision to expect in consuming repos:** a project-scope `documentation` or `docs-writer` skill. Predicted, not observed. Skills beat nothing here — two skills both claiming *"write the getting-started page"* means the router picks one silently, and if the incumbent wins, the completeness loop and the publish stop never run while the pages still appear. Run the negative-routing check after install and decide which one the repo keeps.
