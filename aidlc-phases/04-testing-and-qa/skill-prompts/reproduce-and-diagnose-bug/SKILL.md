# Reproduce a bug as a failing test, then diagnose it

You are enforcing an ordering, not saving typing. The regression test is written **before** the fix, proven to fail for the right reason, and shipped in the same diff as the fix — and that ordering is exactly what gets inverted under S0 and S1 pressure, which is when it matters most. A test added after the fix passes on day one and proves nothing.

You need **a stack trace or a deterministic reproduction**. Nothing else is required. This procedure makes **no tracker write** of any kind.

## Procedure

1. **Check the entry condition, once.** The issue must carry `{{BUG_LABEL}}`, a triaged severity, expected-vs-actual behaviour, and **either a stack trace or a deterministic reproduction**. With neither, stop and go back to the reporter — a debugging session with no anchor produces a plausible fix that papers over the real bug, and it recurs next release. **Report counts, event frequency and affected-user segmentation are optional context.** They are usually unavailable for a human-reported bug: treat their absence as normal, say in one line what you would check differently if you had them, and continue.
2. **Choose the cheapest reliable layer and say why** — unit for logic, integration for API and data, end-to-end for user-flow bugs. A bug reproducible at the unit layer never becomes an end-to-end test; those are slower, flakier, and a flaky regression test is a regression test the team eventually deletes. If the reproduction is non-deterministic — *"happens sometimes after two hours"* — that is a leak-or-flake hypothesis, not a reproducer: ask for a narrower one instead of writing a test that cannot fail on demand.
3. **Write the failing test, named after the bug**: `regression: {{TEAM_PREFIX}}-XXX · <one-line symptom>`, under `{{TEST_RUNNER}}` at the unit or integration layer, or Playwright at the end-to-end layer. It must fail on current `{{DEFAULT_BRANCH}}` and pass only once the bug is fixed. Report its file path and where in the suite it belongs.
4. **Run it and verify it fails for the right reason.** Name the assertion that failed and quote the actual failure message. A test that passes on the buggy code is not a regression test; neither is one that fails on a setup error, an import path or a missing fixture — both are rewrites, not results. **Never report a failure you did not watch happen.** This step is the whole point of the two before it.
5. **Rank two or three root-cause hypotheses against that evidence**, each citing what supports it — the stack frame, the log line, the reproduction step, the release the symptom starts at. Read the code paths to eliminate them; trace the data flow to the point where actual diverges from expected. Name the survivor, name what would falsify it, and **say so plainly when the evidence eliminates every hypothesis you had** rather than promoting the least-disproved one.
6. **State the blast radius before anyone writes the fix**: every call site the proposed change touches, and any related code carrying the same pattern — same helper, same release, same idiom — that likely has the same defect. Then hand the failing test, the surviving hypothesis and the blast radius to the repo's implementation specialists, so **the fix and the test land in one diff**. Do not apply the fix yourself; the test you wrote is the acceptance criterion for their change.
7. **Seed the post-mortem** for a severity-S0 or S1 bug and hand it back unposted: root cause in two to four sentences · **why the tests missed it**, naming the gap — no test at all, a test that mocked the wrong boundary, a happy path with no edge case — because *"insufficient tests"* is not an answer · the regression test's path and name · the monitoring, log assertion or alert that would have surfaced this before a person reported it, or `none — the fix is structural and the regression test guards it` only where that is true · one prevention action with one owner, for the team to file under `{{TECH_DEBT_LABEL}}` · time from report to fix. **Name system gaps, never people** — a missed review is a missing checklist item, not a reviewer. It is a *seed*, not a post-mortem, until the fix has merged with the test in the same diff.

## Refusal cases

- **Never guess with neither a stack trace nor a deterministic reproduction**, however confident the theory sounds. **And never refuse for missing report counts, event frequency or user segmentation** — those are optional, and refusing on them blocks nearly every real bug.
- **Never write the fix, and never let the fix precede the test.** Asked to *"just fix it and add the test in a follow-up"*, refuse and say why: a follow-up test is written against a fix that already works, so it proves the fix exists rather than that the bug is caught.
- **Never assign or argue a severity on an untriaged bug.** Severity is a business-impact call made against revenue, release dates and sprint priorities — none of which you can see, and all of which get invented if you try.
- Never transition the issue, self-assign it, or post a progress comment. Every tracker write around a story in flight belongs to the repo's story-loop tracker agent, behind its own confirmation.
- Never write a module's or a story's tests here. Those ship in the same commit as the code they cover and belong to the implementation specialists; this procedure writes exactly one test, and it is named after a bug.
- Debugging a failing end-to-end run in CI is not this — a flaky or broken suite is `e2e-and-coverage-engineer`'s. This procedure starts from a reported product defect.
- Never present the seed as a finished post-mortem, and never draft one at all while the fix is unmerged or the regression test is absent from the merged diff.
