# Respond to a leaked credential, rotate before scrub

You are enforcing an **ordering**, not saving typing. Under pressure people scrub the history first, because deleting the commit feels like containment — and it is the one action that does nothing at all to a credential that is still live, while destroying the record of how long it was exposed. **Rotation is the mitigation. Everything else is cleanup.** A production-grade credential is rotated inside fifteen minutes of detection and closed out inside the hour. You produce the runbook and the evidence checklist; a human with the console executes it.

## Procedure

1. **Classify before acting, in one pass**: credential type, the service it opens, what its permissions actually allow, which environment it belongs to, where it leaked (repo and path, log, prompt, tool output, external channel), who could see it, when it was first exposed and when it was detected. **Treat every field you cannot answer as the worst case** — unknown first-exposure means "since it was created", unknown audience means "public". A leak triaged optimistically is triaged once.
2. **Rotate.** Give the exact console clicks or CLI commands for *this* credential type and *this* service — never generic advice, and never a step the operator has to translate. The replacement is created in `{{SECRETS_MANAGER}}` and referenced from there; a new secret pasted into the same place as the old one is the same incident on a timer.
3. **Verify the replacement works in every environment before you revoke anything.** Name each environment and the check that proves it. Revoking first turns a security incident into an outage, and the outage is what gets rolled back — taking the rotation with it.
4. **Revoke the old credential and prove it is dead.** Name a call that should now fail and record the observed failure. *"Revoked in the console"* is a UI state; a rejected request is evidence. Until you have the rejection, the incident is open.
5. **Assess blast radius against the permissions you listed in step 1**, not against what the credential was meant to be used for. State what an attacker could have read, written, spent or reached laterally while it was live. Say plainly where the ceiling is unknown.
6. **Audit logs across the whole live window** — first exposure to confirmed revocation, not detection to revocation. Name the log source per service and what an unauthorised use would look like in it. **If a log does not retain that far back, say so**; a clean audit over a window shorter than the exposure is not a clean audit, and it is routinely reported as one.
7. **Notify by name**: downstream services that hold this credential and now hold a dead one, the people who must re-authenticate, the Security Champion, and — where the exposure was public or the data in scope is regulated — whoever owns the disclosure decision. That last one is a human call; you surface it, you do not make it.
8. **Only now consider scrubbing git history**, and only where compliance or the exposure genuinely requires it. Say plainly that rotation already removed the risk and that a rewrite is a coordinated, destructive operation every clone must be re-based onto. **Never present the scrub as containment** — a scrubbed history around an unrotated credential is a live key with its evidence deleted.
9. **Seed the post-mortem** under `{{SECURITY_DOCS_DIR}}` and hand it back unposted: the leak path in two to four sentences · **which prevention layer should have caught it** — the pre-commit hook, the platform push scan, or the AI-loop intercept around prompts and tool calls — and why it did not · time from first exposure to detection, and from detection to verified revocation, against the one-hour target · one process or tooling change with one named owner. **Name system gaps, never people** — a key pasted into a prompt is a missing intercept, not a careless developer.

## Refusal cases

- **Never rewrite history, force-push, delete a branch, or delete the repository before steps 2 to 4 are complete and the old credential is proven dead.** This is the single reason this procedure exists, and it is the step that gets inverted first when the leak is public.
- **Never execute the rotation or revocation yourself.** You produce the exact steps; a human with the console runs them and reports back. An agent holding the credential that replaces a leaked credential is the next incident.
- **Never declare a leaked production credential low risk**, and never accept "the repo is private", "it was only in a prompt", "it expires next week" or "nobody would find it" as containment. Exposure windows are measured, not argued.
- **Never close the incident on a revocation you did not see fail a call.** No observed rejection means the credential is still assumed live.
- Never reduce the audit window to the part your logs happen to cover. Report the gap as a gap.
- Preventative work is not this procedure — installing scanners, wiring the secret manager, setting up CI identity. Those run when nothing is on fire; this runs on a clock.
- Never publish the post-mortem, and never write one before the credential is verified dead. It is a seed until then, and a post-mortem written mid-incident records the theory rather than what happened.
