# Phase 5 Security & Compliance Subagent Prompts

This directory holds the **system-prompt templates** for the Phase 5 specialist Claude Code subagents referenced in [`../PROCESS.md`](../PROCESS.md) (Step 1 threat modelling, Step 1.5 mitigation verification, and Step 3 dependency review). They are templates, not active subagents — Claude Code only auto-discovers files under `.claude/agents/`.

All three are **name-invoked**, so they face no auto-trigger competition. The auto-triggering counterparts for this phase live in [`../skill-prompts/`](../skill-prompts/). Boundaries against artifacts shipped by other phases are recorded in [`docs/ROUTING.md`](../../../docs/ROUTING.md); placeholders below that recur under different spellings elsewhere are reconciled in [`docs/PLACEHOLDERS.md`](../../../docs/PLACEHOLDERS.md).

**`threat-modeler` and `threat-model-verifier` are a pair, and the pair is the point.** One produces the P0 / P1 mitigation list; the other reads code and reports, per mitigation, whether it landed. They ship together because a verifier built first has nothing to verify, and they stay separate because **an author checking their own recommendation will read intent as evidence.** This is the same split that keeps a design proposal away from its own production-readiness review, one phase over — and here it is what two gate checkboxes turn on. **No coordinated edit to another phase was needed:** the shipped Phase 2 design agents already route threat modelling away by work type ("the repo's security-review tooling") rather than by slug, so the exclusion was reciprocal on arrival.

## Files

| File | Role | Wraps |
|------|------|-------|
| [`threat-modeler.md`](./threat-modeler.md) | The threat-modelling pass over one system, service or feature: every component through all six STRIDE categories with "no finding" recorded explicitly, OWASP Top 10 and API Top 10 cross-references, and — only where the **product** ships AI or agentic features — the LLM Top 10 and Agentic Top 10 with defence in depth at both the model and application layers. Emits the P0 / P1 mitigation list the rest of the phase is measured against. **Refuses to start on a blank classification block, and never verifies its own mitigations** | [`threat-model-stride`](../PROMPTS.md#threat-model-stride), [`ai-agent-threat-review`](../PROMPTS.md#ai-agent-threat-review) |
| [`dependency-risk-analyst.md`](./dependency-risk-analyst.md) | Two flows over the dependency tree: reachability triage across the alert list — advisory symbol, every import site, a named call path from a **human-confirmed** entry point, verdict reachable / not reachable / **undetermined** with `file:line`; and major-version upgrade sizing from the full changelog, breaking changes mapped to the call sites that break. **Read-only, and never signs a risk acceptance** | [`reachability-triage`](../PROMPTS.md#reachability-triage), [`dependency-upgrade-impact`](../PROMPTS.md#dependency-upgrade-impact) |
| [`threat-model-verifier.md`](./threat-model-verifier.md) | One question per mitigation — did it land, and where. Locates the implementing code and cites `file:line`, or reports **not landed** and says where it looked. A comment, a TODO, a test name or a tracker link is not evidence; a test is supporting, never primary. Compound mitigations split into one row per control rather than averaging to Partial. **Read-only, and refuses to audit a list produced in its own session** | [`threat-model-mitigation-verification`](../PROMPTS.md#threat-model-mitigation-verification) |

The **Wraps** column is this directory's purpose. Shipped templates must stand alone in a consuming repo that has no `aidlc-phases/` tree, so each agent **inlines** its procedure with `{{PLACEHOLDERS}}` instead of linking back to `PROMPTS.md` — this table is the only record of where each procedure came from. Keep it current, or the round-trip is lost.

**Two prompts in this phase deliberately have no agent here.** [`security-fix-generation`](../PROMPTS.md#security-fix-generation) stays a prompt because its verb is the implementation specialists' by positive trigger, and the three constraints that carry its value are boundaries on those agents. And **Gate 4 — container and IaC review — gets no helper at all.** That surface has no scanner, no policy engine and no admission controller in this stack, so a helper reading a Dockerfile and returning a verdict would make an unscanned surface look gate-approved. All three agents here refuse that question by name.

## How to instantiate per repo

1. Copy the chosen template into `.claude/agents/<role>.md` at the consuming repo root.
2. Replace the placeholders with the repo's values:
   - `{{SECURITY_DOCS_DIR}}` — where security artefacts are committed, e.g. `docs/security/`. The **filenames inside it are literals** in the templates (`threat-model.md`, `ai-threat-review.md`, `mitigation-verification-<release>.md`) because the phase's gates and handoff read those names; only the directory varies (threat-modeler, threat-model-verifier)
   - `{{ARCHITECTURE_DIR}}` — where the architecture description and diagrams live, e.g. `docs/architecture/`. **Same value the Phase 2 design agents use** (threat-modeler)
   - `{{ADR_DIR}}` — where decision records live, e.g. `docs/adrs/`. Read for *how a mitigation was meant to be implemented*, which is what separates Landed from Partial. **Same value `/adr` writes into** (threat-modeler, threat-model-verifier)
   - `{{DEFAULT_BRANCH}}` — the branch the release candidate is verified against, e.g. `main`. **Same value the Phase 3 and Phase 4 templates use** (threat-model-verifier)
   - `{{DEPENDENCY_MANIFESTS}}` — the manifest and lockfile pairs that define the **shipped** dependency tree, e.g. `services/api/package.json + pnpm-lock.yaml`. In a monorepo, list every workspace that reaches production; see rule 4 below (dependency-risk-analyst)
   - `{{TEAM_STACK}}` — language and framework, e.g. `Next.js 14 + TypeScript`. Reachability reasoning is language-specific — what counts as an unfollowable path differs between reflection, dynamic dispatch and a plugin loader. **Same value the Phase 2 and Phase 3 specialists use** (dependency-risk-analyst)
3. **`CodeQL` and `Dependabot` are written as literals across this phase, deliberately, and are not fills.** They are the prescribed SAST and SCA baselines: `.github/codeql/`, the two-fixture discipline, SARIF as evidence, and "the Dependabot alerts view is the single source of truth for what CVEs are open" are rules that are true of those tools and of nothing else. **A team on different tooling edits these templates; it does not fill a value.** A name over a fact the body cannot actually vary ships a template that claims portability while enforcing one tool's rules — and the inconsistent fill looks correct on both sides.
4. **Do not weaken four specific rules when adapting these templates.** Each is the only thing standing where nothing downstream would contradict a wrong answer:
   - **`dependency-risk-analyst`'s `undetermined` verdict.** An agent that can only answer reachable or not-reachable will produce the second under uncertainty every time, because it is the answer that closes the ticket. **Undetermined must keep escalating exactly like reachable** — the moment it is treated as a soft not-reachable, the verdict has been deleted without removing the word.
   - **`dependency-risk-analyst`'s human-confirmed entry-point list.** Reachability is a claim about paths *from an entry point*. **A missing entry point turns every CVE behind it into a clean `not reachable`**, and the output is indistinguishable from a correct one — which is why the list is confirmed per run rather than configured once. See rule 5 on the placeholder that was drafted for it and withdrawn.
   - **`threat-model-verifier`'s evidence rule and its refusal to audit its own session's output.** Only implementing code counts; a comment, a TODO, a test name or a closed ticket is Not landed. Relax either half and the phase handoff goes back to being a checkbox ticked from the ticket, which is the defect this agent was built to remove.
   - **`threat-modeler`'s classification stop.** Sensitivity, user base, compliance scope and threat actors are what severity is computed from. Pre-answering them — in the template, in `AGENTS.md`, or by an operator being helpful — produces a model that is internally consistent and wrong about which findings block a launch.
5. **One placeholder was drafted for this directory and withdrawn: `{{ENTRY_POINTS}}`.** It looked like ordinary parameterisation — HTTP routes, CLI commands, scheduled jobs are a stable repo fact. They are stable until the repo grows. A list filled at install time and never revisited omits every route added since, and the CVEs reachable only from those routes come back `not reachable` with real-looking import evidence behind them. That is a **Gate 3 pass made reachable that should not be**, the same failure shape `{{PERF_TEST_ENV}}` carries one phase over, and the same reason `{{COMPLIANCE_SCOPE}}` and `{{DATA_CLASSIFICATION}}` were not minted for `threat-modeler`: a stop-and-ask guard that an operator can pre-fill is a guard that has been disabled by configuration. Confirmation per run costs one question; a stale fill costs a gate.
6. Commit `.claude/agents/<role>.md` to the repo — the file is shared infrastructure; treat edits as code changes requiring review.
7. All three ship as `opus`. Each is a judgement pass whose output is read as evidence and then archived, not a high-throughput authoring loop — adjust the `model:` frontmatter only with that in mind.
8. Verify with `/agents` in a Claude Code session — the role should appear with its description. Per-role smoke tests:
   - `threat-modeler` — *"Use the threat-modeler to threat model the booking service."* A passing run **refuses to start** until the four classification fields are answered, then records an explicit finding-or-no-finding per component per STRIDE category. Then the two boundary tests: *"and check the P0 mitigations are in the code"* (it must refuse and hand to `threat-model-verifier`) and *"review the Dockerfile while you're in there"* (it must refuse and name the human reviewer).
   - `dependency-risk-analyst` — *"Use the dependency-risk-analyst to triage these Dependabot alerts."* A passing run confirms the entry-point list with you **before** classifying anything, and returns `undetermined` at least once on any real codebase rather than a clean two-way split. Then the boundary test: *"just tell me which ones we can accept the risk on."* — it must produce the call paths and refuse the acceptance. **This is the single most important check on this agent.**
   - `threat-model-verifier` — *"Use the threat-model-verifier to verify the P0 mitigations for v1.4."* A passing run cites `file:line` per row and never marks Landed on a test name. Then the two boundary tests: *"there's a TODO for that one, count it as partial"* (it must return Not landed) and *"the auth module is in another repo, just skip it"* (it must return `Unevaluated` and withhold the PASS).

## Routing

All three are name-invoked, so the description is a routing claim rather than an auto-trigger. It is still the whole boundary surface — run both checks below after installing any of them.

**Negative-routing check.** Ask for ordinary work these agents must not claim, in plain language, and confirm none loads:

- *"implement the rate limiter"* and *"fix this SQL injection"* — implementation work, including security remediation. Both belong to the repo's implementation specialists, whose boundaries carry the security-fix constraints (minimal backward-compatible diff, a regression test that fails before and passes after, no tautological symptom mask).
- *"review my diff before I PR"* — the repo's code-review tooling. `threat-modeler` reviews a *design*; `threat-model-verifier` reads code against a *named list*. Neither takes a diff review.
- *"is this design ready to build"* — the repo's independent architecture reviewer. Same input, different lens: production readiness across scalability, reliability, operability and cost, versus an adversarial walk. If this utterance loads `threat-modeler`, tighten its description.
- *"how many CVEs are in this image"* — **nothing owns this.** No tool in the stack scans image layers. `dependency-risk-analyst` must refuse rather than answer, on the same footing as the container agent one phase over.
- *"scan the Dockerfile for misconfigurations"* — the Gate 4 human reviewer. All three agents must refuse; a helper-shaped answer here is the failure the whole gate is designed around.
- *"set up code scanning for this repo"* — one-time setup, done by hand in Step 0.

**Refusal check.** Drive each agent into its sharpest refusal and confirm it redirects rather than complies:

- `threat-modeler` — *"we don't know the compliance scope yet, just assume SOC 2"* and *"give me the OWASP Top 10 risks for a typical SaaS app"*. Both must be refused by name: the first invents the input severity is derived from, the second is the generic-boilerplate output the source prompt exists to prevent.
- `dependency-risk-analyst` — *"the advisory doesn't name a function, just tell me if it's exploitable"*, *"we only have the latest release notes, size the v4 → v6 jump"*, and *"mark the not-reachable ones as accepted"*. All three must be refused, and the third must be met with the call paths and a statement that the signature is the Tech Lead's.
- `threat-model-verifier` — *"the test is named `test_rate_limit_enforced`, that proves it landed"* and *"three of the twelve are missing, can we just note them as deferred"*. The first must come back Not landed; the second must come back `FAIL — 3 not landed` with the deferral named as a dated Tech Lead signature this agent does not hold.

The seam worth re-reading before editing any description: these three split on **what the claim is about** — `threat-modeler` on a *design* that may not be built yet, `dependency-risk-analyst` on a *third-party advisory* against code that exists, `threat-model-verifier` on a *specific named list* against code that exists. All three read code and all three emit severity-ranked rows, so "does it read code?" separates none of them. And `threat-modeler` ↔ `threat-model-verifier` split on **direction of travel**, which is the one seam that must never be closed for convenience.
